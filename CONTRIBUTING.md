## Как я могу помочь?

### 🐛 Сообщение об ошибках

Если вы нашли баг:

1. Убедитесь, что баг еще не был зарепортен в Issues
2. Создайте новый Issue с тегом `bug`
3. Подробно опишите проблему:
   - Шаги для воспроизведения
   - Ожидаемое поведение
   - Фактическое поведение
   - Скриншоты (если применимо)
   - Версия приложения
   - Версия Android
   - Логи ошибок

### 💡 Предложение новых функций

Есть идея для улучшения?

1. Создайте Issue с тегом `enhancement`
2. Опишите функцию и её назначение
3. Объясните, почему это будет полезно
4. Если возможно, предложите реализацию

### 📝 Улучшение документации

Документация никогда не бывает идеальной:

- Исправление опечаток
- Улучшение существующих разделов
- Добавление примеров
- Перевод на другие языки

### 💻 Написание кода

Хотите добавить новую функцию или исправить баг?

1. Найдите Issue или создайте новый
2. Сообщите, что работаете над этим
3. Следуйте процессу разработки (см. ниже)

## Процесс разработки

### 1. Форк и клонирование

```bash
# Форкните репозиторий на GitHub
# Затем клонируйте свой форк
git clone https://github.com/ваш-username/inventory-checker.git
cd inventory-checker
```

### 2. Создание ветки

```bash
# Создайте ветку для вашей функции/исправления
git checkout -b feature/название-функции
# или
git checkout -b fix/название-бага
```

### 3. Установка зависимостей

```bash
# Backend
cd backend
npm install
cd ..

# Mobile
cd mobile
npm install
cd ..
```

### 4. Разработка

- Пишите чистый и понятный код
- Следуйте стилю кода проекта
- Добавляйте комментарии для сложной логики
- Тестируйте изменения

### 5. Тестирование

```bash
# Запустите backend
cd backend
npm start

# В другом терминале запустите mobile
cd mobile
npm run android

# Протестируйте все функции
# Убедитесь, что ничего не сломалось
```

### 6. Коммит изменений

```bash
git add .
git commit -m "Описание изменений"
```

См. раздел [Коммиты](#коммиты) для правил написания сообщений.

### 7. Push и Pull Request

```bash
git push origin feature/название-функции
```

Затем создайте Pull Request на GitHub.

## Стиль кода

### JavaScript / React Native

- **Отступы**: 2 пробела
- **Кавычки**: Одинарные `'` для строк
- **Точки с запятой**: Да
- **Именование**:
  - camelCase для переменных и функций
  - PascalCase для компонентов React
  - UPPER_CASE для констант

#### Пример:

```javascript
// ✅ Хорошо
const userName = 'John';
const API_KEY = 'abc123';

function getUserData(userId) {
  return axios.get(`/api/user/${userId}`);
}

const HomeScreen = ({ navigation }) => {
  return (
    <View style={styles.container}>
      <Text>Hello</Text>
    </View>
  );
};

// ❌ Плохо
const username = "John"  // двойные кавычки, нет точки с запятой
const api_key = 'abc123'  // snake_case

function get_user_data(user_id) {  // snake_case
  return axios.get('/api/user/' + user_id)  // конкатенация вместо шаблонов
}
```

## Коммиты

### Формат сообщения коммита:

```
тип: краткое описание

Подробное описание (опционально)

Связанные Issues (опционально)
```

### Типы коммитов:

- `feat`: Новая функция
- `fix`: Исправление бага
- `docs`: Изменения в документации
- `style`: Форматирование кода (без изменения логики)
- `refactor`: Рефакторинг кода
- `perf`: Улучшение производительности
- `test`: Добавление тестов
- `chore`: Изменения в сборке, зависимостях и т.д.

### Примеры:

```bash
# Хорошие коммиты
git commit -m "feat: добавлен поиск по инвентарю"
git commit -m "fix: исправлена ошибка загрузки цен"
git commit -m "docs: обновлен README с инструкциями по установке"
git commit -m "refactor: улучшена структура компонента ItemDetail"

# Плохие коммиты
git commit -m "обновление"
git commit -m "фикс"
git commit -m "работает"
```

### Детальный коммит:

```bash
git commit -m "feat: добавлена фильтрация инвентаря

- Добавлен компонент FilterBar
- Реализована фильтрация по редкости
- Реализована фильтрация по цене
- Добавлены тесты

Closes #42"
```

## Pull Requests

### Перед созданием PR:

- ✅ Код работает и протестирован
- ✅ Нет конфликтов с main веткой
- ✅ Следует стилю кода проекта
- ✅ Добавлены комментарии (если нужно)
- ✅ Обновлена документация (если нужно)

### Шаблон PR:

```markdown
## Описание
Краткое описание изменений.

## Тип изменения
- [ ] Bug fix (исправление бага)
- [ ] New feature (новая функция)
- [ ] Breaking change (изменения, ломающие совместимость)
- [ ] Documentation update (обновление документации)

## Как протестировать
Шаги для тестирования изменений:
1. Шаг 1
2. Шаг 2
3. ...

## Скриншоты (если применимо)
Добавьте скриншоты для визуальных изменений.

## Чеклист
- [ ] Код протестирован
- [ ] Нет предупреждений в консоли
- [ ] Документация обновлена
- [ ] Коммиты следуют стандартам
```

### Процесс ревью:

1. Создайте PR с подробным описанием
2. Дождитесь ревью от мейнтейнеров
3. Внесите запрошенные изменения
4. После одобрения PR будет смержен
